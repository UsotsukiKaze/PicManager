# Pixiv-ol 清晰预览与加载提速方案

2026-10-04。连接复用、独立下载额度、头像并行、转码限制及私有协商缓存已实现。测试使用本机当前 Clash 路径；公网服务器和更高 DPR 画质分层仍需后续验证。下文另有未实施的后续方案，不能把目标时间当成实测保证。

## 当前链路与瓶颈

列表走 `/previews/{pid}`，从 Pixiv 下载后生成不超过 800px 的 WebP；详情走 `reader-preview`，优先使用 master1200 清晰预览，原图另行缓存供入库使用。已有服务器磁盘缓存、前端 40 项 / 48MB Blob 缓存、悬停预取、下一页预取及相同文件的下载锁。

本次已处理：

- 头像和清晰图同时请求，悬停预取也不再串行等待头像；账号媒体范围变化会中止旧 Blob 请求。
- CDN 下载按列表、详情、头像、原图使用独立持久 HTTPX 连接池与有界队列，原图入库缓存及校验抽样也遵守后台原图额度，不挤占详情额度。
- `PIXIV_MEDIA_DOWNLOAD_WORKERS=14` 为默认总预算（限制到 8..20）；`PIXIV_MEDIA_PREVIEW_WORKERS=8` 为列表目标额度（限制到 1..12 且不超过总预算减 6）。详情、头像、原图各保留 2 个名额，总额度不会超过预算。等候空位最多 8 秒，网络连接最多 8 秒，正文仍沿用原请求超时。
- 代理 URL、超时或额度变化时重建池，已经在下载或排队的旧请求先结束再释放旧池；服务退出关闭池。继续使用已配置的 Clash，不会在失败后改走直连，不将登录令牌放进 CDN 池，抑制共享客户端的 CDN Cookie。
- 列表、清晰预览和头像采用 `private, no-cache, must-revalidate` + ETag，权限、账号版本、作品可见性与优选夹归属/所选页复核后才能返回 304；共享 CDN 始终 `no-store`。原图和优选夹本地原图缩略图保持现有私有策略。
- WebP 转码并发限制为 2，分辨率、master1200 来源、编码质量保持原值。缓存目录统计改为每 60 秒或接近配额时扫描，在途文件额度单独记录，失败释放预约；不在每次冷请求中持全局文件锁遍历目录。

同一 Clash 路径上的实施前对照：8 张列表缩略图从约 1.18 秒降至连接池 4 路约 0.44 秒、8 路约 0.33 秒；保留原后端、只去掉头像串行后，详情约 1.6 秒降至 1.12 秒。此为对照实验数据，正式实现的网络长尾仍需持续观察。独立详情额度用于保护响应性，不能只增加总并发。

## 图片质量分层

| 场景 | 默认策略 |
| --- | --- |
| 列表卡片 | 使用 480 / 800px 缩略图，按实际卡片宽度和 DPR 选择，裁剪由 CSS 完成 |
| 详情初开 | 立即放大已加载的缩略图，保留模糊与加载动画；后台下载无裁剪 master1200 |
| 大屏 / 放大阅读 | 当预览像素不足覆盖显示区域 × DPR 时，允许切换更高分辨率或原图；保留清晰预览直到新图解码完成 |
| 多 P 翻页 | 当前页最高优先级，仅预取相邻 1 页；快翻时取消无用请求 |
| 入库 | 原图后台缓存与读取，独立于预览，不把原图下载放在详情首次展示的关键路径 |

1200px 预览在高 DPR 或放大阅读时可能不足，不能承诺它在所有屏幕上等同原图清晰度。WebP 默认质量建议 86，经过线稿、文字、渐变对照后确定；仅当转码显著减小体积时才用转码结果。不要为 1200px 文件再制造 2400px 放大图，也不虚构 Pixiv 不提供的清晰规格。

## 后续分层与优先级方案（待实施）

后续在现有有界额度上加入请求优先级和自适应退避：详情优先于可见卡片，可见卡片优先于悬停 / 下一屏预取。预取只在空闲和网络良好时运行；慢网、超时或 429 时降低并发并退避。列表已经支持可配置额度，但尚未自动根据 RTT 改变额度，不默认几十线程抢带宽。

API 推荐 / 关注请求继续遵守现有节流，不和图片 CDN 下载使用同一调度队列。校验线程、入库任务、图片下载队列各自设额度，避免增加校验线程却不能加速浏览。同步后端可先保留现有架构，用有界任务队列和连接池完成，无需为了图片并发立即迁移整个服务。

前端也需要可取消的优先队列：先发当前详情、首屏可见卡片；下一屏限制预取范围；切换作品、切换模式或离开 Pixiv 页面后取消失去用途的请求。同一 PID / 页码 / 规格合并下载；预取命中项在点击后提升优先级，避免低优先级请求挡住用户操作。

## 缓存与连接复用

1. 复用 HTTPX 连接池，设置连接数与 keep-alive 上限；账号令牌、登录请求和 CDN 图片连接隔离，仍逐次检查目标与重定向。代理配置改变时重建池，服务退出关闭池。
2. 浏览器采用 `private, no-cache` + ETag：刷新先向服务器验证，内容未变返回 304。鉴权、账号版本、作品可见性与优选夹归属检查必须先完成，再允许 304；禁止共享 CDN 缓存。URL 加账号媒体版本与图片规格，避免账号切换复用错误图片。服务端继续保留当前私有缓存，禁止删除现有鉴权换取速度。
3. 缩略图和详情使用同一媒体标识体系，但按规格分层；后续可将已实现的低频配额检查进一步移入后台 LRU。当前 WebP 只生成一次、同时转码 2 个任务，避免 CPU 编码拖累下载。
4. 刷新时先显示现有推荐批次，再异步更新；获取新批次后只预热首屏和少量下一屏图片，不要等整批缓存完成才渲染，也不下载整个推荐集的原图。

### 正式实现的本机验证

沿用当前 Clash、真实作品数据和未经替换的下载/缓存/前端代码，使用独立冷缓存目录：8 张列表缩略图首次建池整批 1.96 秒，连接池建立后连续两轮约 0.37 秒；8 张清晰预览约 0.94～1.67 秒。原图与列表同时下载时，两张新详情中位约 0.40 秒。三轮列表与详情的条件请求全部 304，不传图片正文。

浏览器直接加载实际 JS/CSS，无请求拦截地验证缓存：12 张卡片首屏三轮约 1.02 / 0.61 / 0.58 秒；刷新约 0.24 / 0.14 / 0.15 秒，每轮 12 张均由浏览器发条件请求、服务器返回 304。清晰详情三轮约 1.17 / 0.50 / 0.45 秒，均保持 783×1200；人为延迟头像 3 秒后，已经缓存的清晰图仍约 0.40 秒展示，确认头像不再阻塞。浏览器无 JS 错误。
