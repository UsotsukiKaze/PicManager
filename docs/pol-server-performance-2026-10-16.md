# POL 服务端性能修复（2026-10-16）

排查及部署目标：192.168.18.7:8777，Windows，部署时版本 1667032。服务器当前约有 3,129 张库图、3.8 万条作品记录，数据库约 151 MB。

## 已实施

- 快照只累计成功写入；普通读取、无变化提交、回滚及更新零行不累计。达到原有 50 次提交阈值后通知独立后台线程，合并请求并限制备份频率。备份文件的原子发布、完整性检查和仅在数据库缺失时恢复的规则保留。
- 快照文件锁和提交计数锁分离，请求不再等待整个 SQLite 备份和完整性检查。每日快照也进入同一后台队列，失败后自动重试。
- 推荐画像按数据库引擎、标签索引版本、账号版本、所有者、模式与偏好缓存，最多 8 项、有效期 60 秒。返回独立副本；相同输入的并发计算合并。提交训练相关改动后失效，回滚不失效。
- 图库与关联标签、喜欢、优选夹作品数据、映射、偏好和收藏状态变化后，画像重新计算。后台任务的进度和账号同步游标变化不使画像失效。
- 背景标签频率与质量参考独立短期缓存：点赞会更新个人画像，同时保留与本次点赞无关的背景统计。映射和原生标签变化会改变缓存键。新增候选对背景统计的影响最长延迟 60 秒；其他进程直接修改数据库也通过过期机制更新。
- 训练数据和质量参考查询只读取必要列。排序期间预计算候选标签集合和已选角色计数，保留原评分、作者限制、探索配额和时间分布规则。
- 详情先使用现有卡片数据展开并加载预览，异步核实已入库和优选夹状态；状态核实前禁止提交。核实失败时允许正常关闭、重新打开重试。

## 验证

117 项后端测试、10 项 POL 浏览器测试通过，前端类型检查与构建通过。浏览器回归专门阻塞已入库查询，确认弹窗与清晰预览仍能显示，随后正确更新“已入库”并保持禁止重复加入。

服务器只读分析使用同一推荐实现和当前数据库。画像阶段启用 cProfile，含分析器开销；排序阶段未启用分析器。未使用数据库会话凭据，也未调用需登录的推荐刷新接口，因此以下不是用户点击至整批推荐显示的端到端时间。

| 阶段 | 修复前观察 | 修复后只读复测 |
| --- | --- | --- |
| 公开接口 | 常规 8–36ms，快照附近出现约 3 秒停顿 | 连续 36 次，中位 13ms，最大 43ms |
| 完全冷画像 | 只读分析约 13–16 秒 | 约 13.9 秒 |
| 复用画像，含索引准备 | 每轮重复计算 | 约 0.45 秒，SQL 从 62 次降至 8 次 |
| 模拟训练输入失效后重建 | 全量画像 | 约 7.2 秒，保留背景统计；未修改实际喜欢记录 |
| 排序 | 线上任务记录约 5–7 秒 | 首轮约 3.4 秒，复用质量参考后约 0.67–0.71 秒 |

线上任务与只读分析的候选、并发负载不同，不能将这些数值作为严格等量 A/B 或公网延迟承诺。Pixiv 网络召回仍需额外时间；完全冷计算尚有优化空间。

## 部署

已备份服务器数据库和原源文件至项目下 `data/pol-speed-backup-20261016`，并部署到原 8777 服务。服务器前端源码包含较新的页面修改，已取服务器源码在隔离目录构建，发布时保留原资源文件。实例使用独立 Windows 进程运行，已确认 SSH 断开后仍可访问。其他机器人进程未调整。
