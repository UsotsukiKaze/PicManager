## 本轮继续修复结果

### R01 / P1：业务事务和跨资源补偿 — 已修复

新增 `app/file_operations.py` 和 `file_operation_receipts` 表。文件操作前原子持久化意图，数据库提交凭据与图片、任务及审核状态在同一事务中写入；本地暂存源在提交前保留。上传、审核、编辑、删除和重复合并调用方统一控制图片服务的提交，服务方法保留默认提交参数兼容现有直接调用。

事务结束后根据提交凭据决定清理源或回滚目标；进程中断后由独立后台队列恢复。OS 文件租约避免恢复正在执行的操作，失败采用持久化退避重试，不占用派生图工作线程。待审核文件也采用复制后提交，审核拒绝及保留旧图的源清理同样延后。源文件被外部替换后不会按旧清理记录误删；被现有图片引用的文件会保留。

隔离测试包含实际子进程强制退出前/后提交、外层回滚、Session 关闭、保存点提交、删除回滚、远端清理失败及恢复。事务外远端清理失败时，业务逻辑删除已完成，物理对象可能短暂保留，直至重试成功。数据库、原图和 `data/file-operations` 应共同保留；不能主动删除恢复记录。恢复时 R2 配置变化会暂停旧意图，避免在错误的桶执行清理。

### R02 / P1：过期派生图可能先被发布 — 已修复

后台任务先在派生图目录的 `.staging` 编码。在短事务内通过条件 UPDATE 获取写锁并核对任务租约、图片路径、数据库版本及本地文件的 inode/尺寸/修改时间，全部匹配才原子发布并完成任务。失效或失败结果清除暂存；不会重新创建已删除图片的预览。进程退出遗留的任务暂存通过 OS 租约与过期扫描清理，正在工作的暂存不会被误删。

两种派生图均覆盖成功、数据库版本变化、本地原图替换、删除、租约变化及原图消失；同时验证生成期间其他数据库写入可提交。数据库最终提交中断时，已有完整派生图可被后续重试重新生成；不宣称文件系统和数据库具备原生跨资源事务。R2 对象采用项目生成的独立 key；直接在远端覆盖同 key 的外部工具不受本地文件 stat 检查保护。

### R03 / P2：完整本地校验仍假设原图在本地 — 已修复

统一 `ImageService.source_file` 读取上下文。R2 原图下载一次，尺寸、文件大小、感知哈希和缩略图复用同一份暂存；成功及下载/解码失败均清理暂存。本地校验保留标签联动和多页角色的人工选择规则；原图特征改变时清除旧 Pixiv 校验信息。数据库异常向上抛出，不继续提交损坏的事务。

覆盖正常校验、原图特征改变、部分下载超时、无效图片及 HEAD 超时。网络或权限错误不会把现存 R2 记录当成丢失并归档。本地校验位仍由后续重复确认流程负责，不自动绕过疑似重复图片的人工确认。
